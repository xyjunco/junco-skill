# PRD 写作与迭代规范

本规范从连续 PRD 与原型评审中抽取可复用方法。先明确问题、对象、职责和规则，再写产品方案。案例用于解释方法；具体业务模型、术语、角色、阈值、颜色和日期以当前项目为准。

## 1. 资料、诉求与方案

### 先读当前版本和用户样文

读取用户指定的 PRD、项目协作入口、最新反馈和有效决策。识别样文的章节、句长、常用动词、术语、表格、颜色与强调。已有文档按当前结构修订；只更新某一章节时，补齐该章节及必要关联规则。

旧稿、截图、聊天和助手方案各有时点。后续明确决策覆盖早期草稿；已撤回功能从当前正文、流程、原型和验收中同步移除。历史记录可单独保留，避免作为现行规则再次出现。

核对每条资料适用的项目、对象、范围和时点。跨项目案例、旧工作区记录与当前输入不能直接互认事实；确需引用项目上下文时注明来源并确认仍适用。隔离演示或测试按其给定输入取事实，参考规范只提供方法。

### 用户诉求描述工作，而非评审过程

区分以下来源：

| 内容 | 写在哪里 | 表达方式 |
|---|---|---|
| 角色的日常任务、痛点、责任与结果 | 用户诉求、场景、故事 | 角色在什么情境、按什么频率和规模做什么，为何需要 |
| 用户确认的业务对象、口径、范围 | 模型、规则、权限、验收 | 直接写当前有效定义，并记录依据 |
| 卡片、颜色、Tab 等评审意见 | 页面方案与视觉规范 | 转成支持某个决定的信息组织规则 |
| 写作、工具和交付要求 | 工作流程、写作检查、交付记录 | 作为维护方法，不改写成业务方诉求 |
| 助手归纳或设计建议 | 方案与决策记录 | 说明归纳或方案状态，不冒充访谈原话 |

用户故事用「角色 → 情境 → 对象与动作 → 价值 → 验收信号」。有现成实现建议时仍需识别工作目标；已确认的业务事实保持有效。

角色合并后核对职责、读写范围、审批、通知接收和故事。角色数量由项目决定，权限继承要有明确规则。

### 未决事项集中管理

重要事实缺口、权限归属、数据来源、约束或执行机制要可见。集中记录「事项、已有依据、缺失决定、影响、负责人、下一步」，正文在影响规则处引用。

经授权的常规页面布局和按钮文案可直接作为方案写出，在方案层说明其状态。无需给每个字段反复贴「待确认」「建议方案」「建议文案」。界面展示给用户的实际文案。

保持事实、方案、未决决定和验证结果的区别。未知事实仍然未知，不能为使文档显得完整而补成默认值、权限、枚举或已上线能力。

## 2. 产品语言与可读性

### 写责任、动作和结果

将「不要出现什么」还原为正向规则：谁负责、使用什么对象、何时操作、数据如何变化、结果在哪里查看。必要的排除、权限和风险约束保留；避免机械删除所有否定词。

| 难读或像 prompt 的写法 | 产品语义写法 |
|---|---|
| 不将原需求或来源转换量冒充目标 | 原需求量用于核对来源。计划按已确认目标安排数量。 |
| 不自动执行，不直接影响实际量 | 保存记录本次安排；确认提交后创建执行请求。实际结果按执行回执更新。 |
| 不承载完整逻辑，不承担审批 | 列表用于查找和选择对象。详情展示规则与记录；审批页处理审批决定。 |
| 不允许不同口径直接相加 | 数量按资源规格、计量单位和统计范围分组汇总。 |

写作要求留在检查清单，业务规则进入产品方案，设计依据放在背景或决策说明。页面文案不承载 prompt、评审过程或「为什么这样设计」。

### 用短句说清业务关系

按「计算什么 → 用哪些数据 → 怎么计算 → 范围与时点 → 结果用途」表达。一句承担一个主要规则，相邻句保留依赖关系。字段、动作、来源、阈值和结果要具体，少用抽象概括。

### 按规则职责分块

原型同步时先整理新旧信息，再写入正文。一条列表项承担一个职责；若同时包含字段清单、布局、计算口径、范围、阈值和状态，应拆成有短标签的原生段落或列表。字段清单或方案对照适合小表格，单一规则适合短句，不机械套固定分组。

同一条公共规则在模块内有唯一主说明，其他位置仅引用其名称或结论。比较总体、展示子集、修改集合虽有关联，仍分别定义；去重不能合并不同职责。压缩文字保留对象、条件、单位、版本、精度、操作效果和必要边界。

正文先用中文字段公式，每个公式独立成可编辑段落，口径说明紧邻公式：

> 当前交付率 = 累计已交付量 ÷ 预算额度。

> 预计交付率 =（累计已交付量 + 本批发放量）÷ 预算额度。

同一预算单元的多条本批计划合并计算。

先核对原字段字典与变量映射，再写中文公式。符号含义未定义时，保留已知计算关系，并把缺失定义集中列入决策项；不能从附近出现的名词或参考案例推断分母是预算、目标或计划量。

紧邻说明资源规格、地域、预算版本和统计时点。复杂算法确需符号时，在算法附录另列符号定义；业务正文保持可读。

自然文风编辑应保留原句全部业务含义。用户指定 Humanizer 时使用该 skill；PRD 仍需准确的数量、状态、权限和依赖，不添加文学化或宣传性表达。

### 术语、单位与格式

- 同一概念使用项目已确认的唯一称谓。更名覆盖正文、表格、原型、图示、按钮、状态与验收；接口标识按契约保留。
- 数量以「数值 + 单位」表达。资源类型或规格有独立字段时，数量列专注数值与单位。合并缺少独立意义的平行数量列。
- 统一中英文、数字、单位、标点和日期格式，沿用目标文档规范。对象 ID、域名、路径和代码标识保持原样。
- 百分比与百分点区分。两项比率从 46% 到 50%，差值为 4 个百分点；判定用完整精度，展示按规定小数位。

### 颜色、字体与空格

沿用已有文档的字体、字号、标题层级、列表缩进和颜色语义。普通说明及数值使用常规字重；关键动作、阈值、风险和必要结论局部强调。文字过密先调整分组与分块，不靠缩小字号解决。避免整段加粗、给所有引号内名词上色或增加大量提示条。

动作、链接、成功、风险各用其既有语义。处理中、待确认等状态的色彩对应真实含义。富文本编辑保留非目标 run 的字重、颜色、字体、链接和换行。结构与渲染分别检查。

## 3. 对象、动作与跨页一致

### 先辨认交付或执行的对象

分别定义业务需求、计划、执行请求、执行结果、记录、当前持有，以及底层资源或来源记录。物理属性只有在该业务对象真实需要时进入其操作流程。

**项目案例：**池化 Quota 是计划与交付的对象；机器数量和机型不能沿旧模型混入交付动作。独立物理调转模块仍按其物理对象工作。通用方法是识别对象责任，而非让所有产品采用 Quota。

### 拆清动作阶段

| 阶段 | 需要定义的事实 | 常见核对点 |
|---|---|---|
| 计划或配置 | 保存的目标、版本、范围 | 保存是否包含执行效果 |
| 预览或建议 | 拟变更对象、数量、影响 | 计算结果如何采用，原方案如何保留 |
| 提交或受理 | 请求、提交范围、受理结果 | 谁可提交，去重、权限与最新版本校验 |
| 执行与回执 | 实际执行量、失败项、时间、来源 | 请求受理和执行完成的状态区分 |
| 当前持有或有效状态 | 当时存量、归属、变动 | 与累计历史、计划量的关系 |

定义实际业务存在的阶段，不用模板凭空添加流程。每个状态都有事实来源、进入条件、可执行动作及后续效果。

### 模型变更沿对象链传播

建立影响清单：输入字段 → 计划 → 操作 → 请求与回执 → 记录详情 → 列表与大盘 → 权限与通知 → 图示与验收。

逐项检查旧术语、物理属性、错误数量、阶段混淆、计算公式和重复来源。视觉重排后再核对业务含义。单张截图修好只证明该张，不能据此宣称全项目一致。

## 4. 数据、指标与比较范围

### 指标先回答角色的判断

为指标建立「角色与决定、业务对象、含义、来源、单位、时间窗口、统计范围、公式、去重、精度、更新时点、下钻动作」。核心指标必须有可达展示位置；可以分视图或下钻，避免为留白或极简而删掉原始诉求。

区分预算执行、某期计划完成和当前持有快照。年度与月度、累计与本期、计划日期与实际日期、总量与迁移流量分别定义。不同资源、单位或口径分组统计。

### 区分三个范围

| 范围 | 决定什么 | 核对要求 |
|---|---|---|
| 计算或比较总体 | 分母、排名、极值、配平基线 | 覆盖全部同口径可比对象 |
| 展示子集 | 当前筛选、Tab、分页或图表 | 说明它与总体的关系 |
| 修改或执行集合 | 本次实际调整、提交的对象 | 只变更获得操作范围的对象 |

筛选与分页通常改变可见行；是否同时改变计算总体或执行集合，需明确。跨页选择、全文件导入和多计划合并都应有确定规则。

非参与项的展示符号与计算值分开定义。**项目案例：**未涉及本次发放的预算单元显示 `--`，内部新增量按 0 参与全量比较，预算和存量仍有完整数据。它不是「尚需选择」或源数据缺失，也不等同已选计划中的零发放。

比较前后使用一致的基线、单位、版本和时点。阈值来源明确，用完整精度检查；四舍五入后的相同显示值不能证明达标。约束不可同时满足时，明确限制及可执行的处理选择，避免编造漂亮结果。

### 正常样例完整，未知事实单独处理

正常原型有完整、合理、可对账的代表数据，列表与详情、数量与比率、分布与总量相互一致。说明是来源数据还是静态演示值，避免冒充生产事实。

「未提供」「未返回」等占位词不能代替缺少的样例或业务设计。实际存在的空数据、加载、失败、延迟按业务证据单独设计；真实事实缺口进入未决事项。工具连接失败在工作进度中处理，不能转写成正常产品的数据状态。

## 5. 页面组织与展示形式

### 页面按决定分工

写清入口已带入的对象、主任务、需要的信息、动作和完成后的去向。列表已完成选择时，行操作可直接定位该对象；修改选择返回承担选择职责的列表。

重复选择抽屉、只解释步骤的中间页和没有复核价值的成功页会增加成本。预览已经支持最终决定时可直接提交。独立结果页应服务部分成功、长异步任务或必要结果核对。

### 行动引导与静态依据分层

强调区域聚焦当前阶段的目标、关键提示和主操作。身份属性、来源、额度组成、历史记录置于常规信息区域。沿用已确认的行动样式，先理解它的用途再调整。

额度、上限、资源支撑、可编辑量、余额等先定义属于来源、约束、输入还是结果，以及它们的关系。主区展示支持当前决定的核心值，构成与来源按需展开；名称不同但数值相同不自动等于重复，名称相同但口径不同也不能随意合并。

按对象与维度分组，同组字段对齐。版本和来源有唯一主说明，其他位置给简短摘要或入口。状态跟随所属对象或标题；辅助操作靠近所属信息，避免孤立在卡片之间或独占空行。

前后对比采用相同字段顺序、量纲、基线与时间。多对象比较适合对照表或图；少量聚焦结果可用并列卡片。清楚区分当前事实和预计结果。

### 图表与表格各尽其用

趋势、分布、结构和变化使用可读图表；逐条查询、核对和执行使用表格。待办应支持快速定位事项、对象、状态和动作，避免装饰性卡片取代操作信息。

按维度切换的分布视图只展示当前维度，显示数量及必要占比，尺度一致、总量可对账。默认视图排在首位。维度切换、全局筛选和统计范围关系写清。

减少无意义整行占位，使用合适的图表尺寸和主次结构。控制密度靠分组、对齐、取舍和下钻，而非塞满粗体或大面积空白。静态图条长度、刻度、图例和数据也应核对。

## 6. 批量任务与闭环

先明确操作者、周期、规模、对象、来源和提交单位。数百条月度任务应支持一次输入、全批校验与整体提交；少量在线修改可使用多选或编辑表格。相同「批量」名称未必采用相同交互。

**月度批量录入案例：**资源负责人按月上传计划文件，系统解析全部记录，展示汇总及行级校验，用户纠错后一次导入，返回该月计划列表。几十至上百条任务不能退化成逐行新增表单。

写清：

- 输入方式与字段契约：文件、粘贴或来源数据的格式、版本、单位与必填项。
- 全批校验：总行数、可执行数、重复、冲突及错误的定义；跨行约束、整批或部分执行策略。
- 预览与纠错：分页、筛选、错误定位、修订后重新校验；明确执行范围是否仍是完整批次。
- 提交与结果：确切对象及版本、权限、幂等、重试、重复导入规则、回写、审计与返回位置。

仅写已确认或作为当前方案提出的规则。策略未决时集中列出影响，不凭空默认「跳过错误」或「全部失败」。模板下载、额外附件等按任务需要及当前范围决定，用户退出后同步移除。

确认步骤由后果与可逆性决定。批量不天然等于高风险；现有预览能完成最后决定时，直接提交即可。涉及覆盖、不可逆或重大权限/财务/运行影响时展示精确影响和必要选择。

## 7. Milestone 与 Roadmap

先拆独立建设线，再识别接口、数据、审批和执行结果等真实依赖。可独立开发的工作并行；依赖约束具体联调或验收节点，避免把整条线变成另一条线的前置条件。

每个节点应回答「到时能做什么，如何证明」：

| 工作线 / 节点 | 时间或截止 | 可用能力与交付物 | 验收标准 | 前置依赖 | 责任 / 排期状态 |
|---|---|---|---|---|---|
| 录入闭环 | 按估时填写 | 输入、校验、保存、列表核对 | 一组完整数据可正确保存并定位 | 字段与权限契约 | 负责人；建议或承诺 |
| 批量闭环 | 按估时填写 | 全批解析、校验、提交与去重 | 大批量用例可对账、重复提交行为确定 | 录入接口与导入规则 | 负责人；建议或承诺 |
| 回写与恢复 | 按估时填写 | 结果记录、失败恢复与审计 | 成功/失败结果按来源呈现，可恢复 | 执行契约和回执 | 负责人；建议或承诺 |

节点依产品拆为契约就绪、首个可用闭环、核心执行、结果回写与恢复、单线验收、联合验收、灰度和扩围等。不是每条线都套相同数量或日期；验收窗口按能力准备程度错开。

Roadmap 的日期和节点与 Milestone 表一致。时间轴按真实时长比例显示，泳道表达并行，依赖表达前置条件。日期缺少研发人力与估时依据时标为建议排期，列出影响承诺的必要确认项。

## 8. 原位维护与验收

遵从用户指定的文档与工具。Feishu 文档使用对应 skill 和原生能力；用户明确要求不用浏览器时，该约定在后续重试中保持。其他目标使用各自技能，具体认证和写入步骤交由对应 skill。

先读取实时文档及原生结构，定位授权范围。做最小必要补丁，保留非目标段落、表格、样式、链接和附件引用。写入前重读目标以兼容并发编辑，避免旧镜像恢复用户已删除的内容。

最小补丁指最小受影响范围，不是最少块数量。原型同步前先列出本次变化及其在正文中的归属，合并重复规则，再决定替换、拆分或新增原生块。引用依赖旧块 ID 时保留被引用的入口块；其余内容按职责分块，不为维持旧 ID 把新增规则塞成长段。原生列表与局部富文本保留编辑能力，换行不能代替语义分块。

术语、角色、流程和排期变更覆盖内嵌图片、画板和图注。原生图优先保留编辑能力。需要重建时先备份并评估 ID、分组、连线和引用的影响；按用户已有授权及目标工具要求执行，不能把一次重建许可推广到任意后续操作。

连接失败先区分认证/通道与目标状态。写入结果未知时先回读，确认哪些内容已生效，再补剩余部分；明确失败时重试对应操作。保留已完成工作，认证只请求必要权限。

交付前核对：

- 正文：术语、对象、动作效果、计算、权限、未决事项与当前范围；规则职责清楚，公共规则无重复，压缩后业务边界完整。
- 数据：正常样例完整，公式和总量按同口径对账；比较总体、展示子集和修改集合分别符合已定义的范围契约。
- 结构：目标块、表格、链接、富文本、图片、节点分组和连线。
- 视觉：在目标文档的正常宽度与缩放下，查看改动正文及相邻区域的截图，核对字重、颜色、空格、密度、对齐、图表尺度、溢出和裁切；公式、范围、阈值与状态能分别定位。
- 关联：模型、流程、原型和验收已同步，旧方案仅留历史。

将设计建议、文档更新、静态原型验证、运行时验证与用户验收分别陈述。截图替换成功、API 成功或文字检索通过不能单独证明正文可读或视觉正确。未取得正文渲染证据时，交付中说明只完成结构与内容回读；静态原型不能证明后台执行上线。

结果写入指定目标后，聊天给核心变更、验证情况及少量准确链接。给视觉备选时，编号、名称、说明与图一一对应。
